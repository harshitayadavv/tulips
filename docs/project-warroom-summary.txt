PROJECT: WarRoom
GitHub: https://github.com/harshitayadavv/warroom
Live: Deployed on Render (backend) + Vercel (frontend)

WHAT IT IS:
WarRoom is a full-stack multi-agent AI debate platform where four specialized LLM agents debate any topic in real time, streaming token-by-token via WebSocket, with per-turn scoring, fallacy detection, vector-embedding consensus measurement, and time-travel forking across debate rounds. This is Harshita's most technically complex project.

THE FOUR AGENTS:
- AXIOM (Proponent) — argues FOR the topic, temperature 0.7-0.8, analytical and aggressive
- REFUTE (Opponent) — argues AGAINST, temperature 0.8, attacks assumptions and tradeoffs
- VERITAS (Fact-Checker) — neutral auditor, temperature 0.2-0.3, detects logical fallacies
- ARBITER (Moderator) — scores each round, delivers final verdict, temperature 0.3-0.4

TECH STACK:
Frontend: Next.js 14 (App Router), TypeScript, Supabase Auth, native WebSocket, Vercel
Backend: FastAPI, LangGraph, Groq API (Llama 3.3 70B), Supabase (PostgreSQL), Redis, Render
AI/ML: Llama 3.3 70B for debate agents, Gemma2-9b-it for scoring, vector embeddings for consensus measurement

LANGGRAPH STATE MACHINE (7 nodes):
START → round_start → proponent → opponent → fact_checker → moderator → consensus → (loop or end) → judge → END

CONSENSUS ENGINE:
After each round: extracts stance summaries from both agents, embeds them as vectors, computes cosine similarity (0.0-1.0). If score >= 0.85 OR round >= max_rounds, debate ends. Threshold default is 0.85.

DATABASE SCHEMA (Supabase/PostgreSQL):
- debates table: id, user_id, topic, status, config (JSONB), current_round, consensus_score, winner_role, summary, tags
- turns table: id, debate_id, round, agent_role, agent_name, content, score (JSONB), embedding (FLOAT[]), is_interrupt
- checkpoints table: id, debate_id, round, label, state_snapshot (JSONB) — enables time-travel forking
- verdicts table: id, debate_id, winner, summary, key_arguments, final_consensus_score, total_fallacies, confidence

WEBSOCKET EVENTS (14 types):
ping, debate_started, round_started, agent_thinking, agent_speaking, agent_tool_call, agent_tool_result, turn_complete, round_complete, consensus_update, debate_paused, debate_interrupted, verdict_ready, debate_complete

REDIS USAGE:
- pause:{debate_id} — pause signal (HTTP layer cannot write to running LangGraph graph mid-node)
- interrupt:{debate_id} — human interrupt data
- approval:{debate_id}:{request_id} — tool approval responses
- Redis is external to graph — readable/writable from anywhere, unlike LangGraph state

HARDEST BUG:
WebSocket callback stored in LangGraph state caused silent crash after first node. LangGraph's MemorySaver checkpointer serializes state to msgpack — Python functions are not msgpack-serializable. Fix: module-level registry dict (_WS_CALLBACKS) separate from serializable state.

TIME-TRAVEL FORKING:
Checkpoints saved after each consensus_node. GET /debates/{id}/checkpoints lists them. POST /debates/{id}/checkpoints/{cp}/fork creates a new independent debate from that round's state.

FALLACY DETECTION (10 types):
Ad hominem, straw man, false dichotomy, appeal to authority, circular reasoning, slippery slope, hasty generalization, red herring, false analogy, appeal to emotion — detected by VERITAS using LLM-based structured prompting, not rule-based.

MEASURED PERFORMANCE:
Average agent response time: 1-5 seconds. Average round duration: ~7 seconds. Total 5-round debate: ~47 seconds. ~21,000 total tokens per debate.

DESIGN TRADEOFFS:
- LangGraph over sequential chain: needed conditional routing, checkpointing, pause/resume
- Redis for pause signals instead of LangGraph state: HTTP endpoints run in separate async context, cannot inject into running graph
- WebSocket over SSE: needed bidirectional signaling (pause/interrupt from client to server)
- Groq over OpenAI: 10x faster inference, sub-5s agent responses
- Separate scoring model (Gemma2): prevents rate limit collisions with debate agents on same quota
- 6-turn context window per agent (not full transcript): token efficiency without losing focus

KNOWN LIMITATIONS:
- Single Render instance limits ~2-3 concurrent debates before Groq rate limits
- Consensus rarely triggered by genuine agreement — LLMs hold assigned positions strongly, most debates terminate via max_rounds
- Embeddings pipeline had issues with Groq embed_text returning zeros — real consensus scoring limited
- Scoring defaults to 65 when rate limits hit scoring model
- No JWT validation on WebSocket handshake
- No mid-token replay if WebSocket drops during streaming

HARSHITA'S ROLE:
Full stack — designed and built the entire system including LangGraph state machine, all four agent prompts, WebSocket event system, Redis pause/resume, checkpoint/fork system, PostgreSQL schema, and frontend.
