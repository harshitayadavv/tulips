PROJECT: SkyRacer
GitHub: https://github.com/harshitayadavv/SkyRacer
Live Demo: https://sky-racer.vercel.app
Backend API: https://skyracer.onrender.com

WHAT IT IS:
SkyRacer is a full-stack real-time browser game where you control an airplane using hand gestures (camera swipes via MediaPipe) or voice commands (Web Speech API) to dodge obstacles. Built entirely by Harshita Yadav to demonstrate AI/ML integration in a production web app.

TECH STACK:
Frontend: React, Vite, Tailwind CSS, Canvas API, MediaPipe Tasks Vision (WASM + WebGL), Web Speech API, WebSocket API
Backend: FastAPI, Motor (async MongoDB driver), MongoDB Atlas, python-jose (JWT), passlib + bcrypt==4.0.1, google-auth
Infrastructure: Vercel (frontend), Render (backend), MongoDB Atlas, Docker + docker-compose

WHY EACH TECH:
- MediaPipe runs in browser (not server) to eliminate network round-trip latency — gesture detection stays at ~10-15ms GPU inference
- Motor (async MongoDB) instead of PyMongo — sync driver would block FastAPI's async event loop
- Canvas API instead of a game engine — lightweight, no overhead, full control over rendering
- Web Speech API instead of Deepgram/paid STT — free, no API key, Chrome-native, acceptable for demo

GESTURE DETECTION — HOW IT WORKS:
1. Camera frame captured (640x480, 30fps) — stays in browser, never transmitted to server
2. MediaPipe processes frame in ~10-15ms via GPU/WebGL
3. Returns 21 (x,y,z) hand landmarks
4. Landmark 9 (middle finger MCP — most stable palm center point) extracted
5. Pushed into sliding window of 8 frames (~133ms at 60fps)
6. Velocity computed: dx = newest_x - oldest_x, dy = newest_y - oldest_y
7. Dominant axis classification with 0.09 threshold (9% of frame width)
8. On gesture: WebSocket sends ~40 bytes to FastAPI
9. Backend updates airplane position, sends full game state back at 30fps
10. React redraws Canvas

WHY LANDMARK 9:
Most stable point on the hand. Doesn't move when fingers curl or extend. Stays in frame (fingertips and wrist often cut off). Represents true palm center.

VOICE GAME PATH (different from gesture):
- Web Speech API sends audio to Google servers (~200-400ms)
- Returns transcript string ("up", "down", "left", "right")
- Browser matches and calls setGameState() directly in React
- NO WebSocket involved in voice movement — fully client-side
- Score sent to backend via REST only at game end

WEBSOCKET PROTOCOL:
Client → Server: {"type": "gesture", "direction": "left"} (~40 bytes)
Server → Client: {"type": "game_state", "state": {"airplane": {...}, "obstacles": [...], "score": 30, "gameOver": false}} at 30fps

GAME ENGINE LOGIC (backend):
- Runs at 30fps (33ms loop)
- Obstacle spawn: random type (bird/cloud/lightning/UFO), random y position
- Movement: obstacle.x -= speed * game_speed
- Collision: AABB with 15px forgiveness padding
- Scoring: obstacle off left edge = +10 points
- Difficulty: every 100 points, game_speed += 0.1, spawn_interval -= 0.1s

MONGODB SCHEMA:
User document stores: email, hashed_password, google_id, created_at, stats (nested: voice and gesture with games_played/high_score/total_score/wins), achievements array.
high_score update uses MongoDB $max operator — atomic, no race conditions possible.

AUTHENTICATION:
JWT (HS256) + Google OAuth 2.0 + bcrypt password hashing.
JWT payload: sub (user MongoDB _id), exp (7 days), iat.
Google OAuth: Google token → backend verifies with google-auth library → our own JWT returned.
Known gap: No JWT revocation — logout only deletes from localStorage.

DESIGN TRADEOFFS:
- Browser-side MediaPipe vs server-side: eliminates network latency (~200ms saved), reduces server RAM, trades client CPU
- MongoDB vs PostgreSQL: nested user stats document is natural fit, no joins needed, flexible schema for new achievement types. PostgreSQL would be better for complex leaderboard SQL queries and ACID transactions.
- WebSocket vs REST: bidirectional, no polling overhead, server can push game state — REST would require client polling every 33ms
- Web Speech API vs paid STT: free and dependency-free, trades Chrome-only compatibility and ~200-400ms Google server latency

KNOWN GAPS:
- Score lost if WebSocket disconnects mid-game (state in memory only)
- Voice score fakeable (game loop client-side)
- No JWT revocation
- No rate limiting on auth endpoints
- Backend cold start ~60 seconds on Render free tier
- Max ~50 concurrent players on free tier (game loops in memory)

WHAT HARSHITA WOULD DO DIFFERENTLY:
- Global leaderboard with Redis sorted sets instead of MongoDB aggregations
- Move game loop to frontend for horizontal scaling (stateless backend)
- Redis session store so game state survives server restarts
- Mobile gesture support (MediaPipe is desktop-only)
- Add JWT refresh tokens + short expiry for proper revocation

BUGS FIXED:

- Voice recognition stopped after 5 min: stale closure in onend handler — fixed with listeningRef
- bcrypt error: bcrypt 4.1+ broke passlib — pinned bcrypt==4.0.1
- Multiple gestures from one swipe: no debounce — added sliding window clear + 400ms cooldown
- MediaPipe server crash: moved gesture detection to browser entirely
- CORS errors post-deploy: added Vercel URL to FastAPI CORS allow_origins
