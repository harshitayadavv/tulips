PROJECT: WordSmith
GitHub: https://github.com/harshitayadavv/WordSmith
Live Web App: https://word-smith-sand.vercel.app
Backend API: https://wordsmith-backend-iatg.onrender.com

WHAT IT IS:
WordSmith is an AI-powered Chrome extension and web app that transforms text using Groq's Llama 3.1 model. Users paste text, select one or more transformation modes, and get rewritten text in under 2 seconds. Supports chaining multiple transformations sequentially with automatic conflict detection.

8 TRANSFORMATION MODES:
Grammar Fix, Formal Tone, Friendly Tone, Shorten, Expand, Bullet Points, Add Emojis, Tweetify

MULTI-SELECT CHAINING:
Apply up to 8 transforms in sequence. Conflict rules: two "tone" types conflict (Formal + Friendly blocked), two "length" types conflict (Shorten + Expand blocked), "neutral" types (Grammar, Bullet, Emoji, Tweetify) combine freely with anything. 28 valid combinations total.

How chaining works: for Grammar + Formal + Shorten:
- Call 1: original text → Grammar Fix → result 1
- Call 2: result 1 → Formal (original_text param preserves true original) → result 2
- Call 3: result 2 → Shorten (original_text param preserved) → result 3
- 3 DB records written, each shows true original vs its output
- Orchestration is on the frontend, backend is stateless

TECH STACK:
Frontend: React.js, Vite, Chrome Manifest V3 (extension)
Backend: FastAPI, SQLAlchemy ORM, SQLite
AI: Groq API, Llama 3.1 8B instant
Deployment: Vercel (frontend), Render (backend)

WHY EACH TECH:
- Groq over OpenAI: fastest LLM inference available, cheaper, generous free tier
- Llama 3.1 8B over 70B: fast and cheap enough for transformation tasks, sub-2s on warm server
- SQLite over PostgreSQL: zero infrastructure for MVP, SQLAlchemy abstraction means migration to PostgreSQL is same code
- Chrome Manifest V3 over V2: current standard, V2 deprecated by Google — stricter CSP required bundling everything

API ENDPOINTS:
POST /api/v1/transform — main transform endpoint
POST /api/v1/batch-transform — multiple texts at once
GET /api/v1/history — 7-day history
POST /api/v1/history/save — mark as favorite
DELETE /api/v1/history — delete items
GET /api/v1/transformations — list available transforms
GET /api/v1/health — check API, DB, Groq status
GET /api/v1/cache/stats — cache hit/miss stats

DATABASE SCHEMA (single table — transformation_history):
id (UUID), user_id (indexed), original_text, transformed_text, transformation_type (indexed), additional_instructions, processing_time, word_count_original, word_count_transformed, is_saved (boolean — True = permanent favorite), created_at (indexed for 7-day filter), updated_at

7-day retention: every history query filters created_at >= now - 7 days
Favorites: is_saved = True exempts record from cleanup permanently

USER IDENTITY:
Generated as user_{timestamp}_{randomString}, stored in localStorage, sent with every request. Backend trusts whatever user_id is sent.
Known gaps: clear localStorage = lose history, new device = new identity, no cross-device sync, no rate limiting per user.

CACHING:
In-memory Python dict. Key = (text, transformation_type, additional_instructions). TTL = 3600s. Max 1000 entries. Two users sending same text share result. Critical weakness: wiped on every Render restart — real hit rate very low in practice. Fix would be Redis.

PERFORMANCE:
Single transform on warm server: 800ms-1.8s. Cold start on Render free: 30-60 seconds. 3-transform chain warm: 3-5 seconds. Cache hit: ~10ms.

CHROME EXTENSION SPECIFICS (Manifest V3):
Background scripts are Service Workers — ephemeral, not persistent. Stricter CSP — all scripts must be bundled, no remote scripts. If popup closes mid-transform: frontend fetch abandoned, but backend continues, result saved to DB. User finds it in history when they reopen.

CONFLICT DETECTION:
Lives entirely on frontend — backend has no conflict awareness. Known gap: semantic conflicts like Bullet + Tweetify not detected.

DESIGN TRADEOFFS:
- SQLite vs PostgreSQL: zero infrastructure for MVP, accepted write contention above 30 concurrent users
- Frontend orchestration vs backend chaining: stateless backend is simpler and more scalable, trades extra API calls from client
- In-memory cache vs Redis: zero setup, accepted cache loss on restart
- Temperature 0.3: consistent and deterministic output, traded creativity for reliability

KNOWN SECURITY GAPS:
No authentication, CORS wildcard, no rate limiting (Groq budget fully exposed), prompt injection possible via additional_instructions field, history unprotected by user_id alone.

WHAT HARSHITA WOULD DO DIFFERENTLY:
- PostgreSQL for concurrent writes and persistent storage
- Redis cache that survives restarts
- Google OAuth for real cross-device user identity
- Rate limiting with slowapi
- Streaming responses so users see text transform in real time
- Server-side conflict detection for robustness
- Publish to Chrome Web Store
