# WordSmith — Complete Interview Summary

---

## One Line Description
AI-powered Chrome extension that transforms text using LLMs with 8 modes, multi-select chaining, history tracking, and favorites — built with React, FastAPI, SQLite, and Groq API.

---

## What It Does
- Paste text → select transformation → get AI-rewritten text in under 2 seconds
- 8 transformation modes — Grammar Fix, Formal, Friendly, Shorten, Expand, Bullet Points, Emoji, Tweetify
- Chain multiple transforms sequentially — Grammar → Formal → Shorten applied one after another
- 28 valid multi-select combinations with automatic conflict detection
- 7-day auto-expiring history, permanent favorites system
- Works as both Chrome extension and standalone web app

---

| Technology | Why |
|---|---|
| React.js | Complex UI state — conflict detection, loading states, tabs |

## System Architecture

```
Chrome Extension (React popup)
         ↓
     api.js (fetch calls)
         ↓
FastAPI Backend on Render
    ↓           ↓
 Cache        Groq API
 (memory)   (Llama 3.1)
    ↓           ↓
      SQLite Database
```

**Request flow:**
1. User selects transform in popup
2. Frontend calls POST /api/v1/transform
3. Backend validates input
4. Checks in-memory cache — hit = return instantly
5. Miss = call Groq API with crafted prompt
6. Save result to SQLite
7. Return response to frontend

## Relational Schema

**Single table — `transformation_history`**

| Column | Type | Description |
|---|---|---|
| id | String(36) UUID | Primary key |
| user_id | String(100) | Identifies user, indexed |
| original_text | Text | True original before any chaining |
| transformed_text | Text | Final output |
| transformation_type | String(50) | Which transform was applied, indexed |
| additional_instructions | Text | Optional user custom instructions |
| processing_time | Float | Groq response time in seconds |
| word_count_original | Integer | Word count before transform |
| word_count_transformed | Integer | Word count after transform |
| is_saved | Boolean | False = expires, True = permanent |
| created_at | DateTime | Used for 7-day retention filter, indexed |
| updated_at | DateTime | Auto-updates on change |

**Indexes on** — user_id, transformation_type, is_saved, created_at

**No foreign keys** — single table design, no relationships

**7-day retention logic** — every history query filters `created_at >= now - 7 days`

**Favorites logic** — `is_saved = True` exempts record from cleanup, persists forever

## Transform Request Schema

```
POST /api/v1/transform
{
  text: string (1-5000 chars, required)
  transformation_type: enum (required)
  additional_instructions: string (optional, max 500)
  user_id: string (optional, defaults to anonymous)
  original_text: string (optional, used for chain tracking)
}
```

**original_text field** — when chaining transforms, frontend passes the true original text so every DB record stores original vs final, not intermediate steps

---

## Multi-Transform Chaining — How It Actually Works

For Grammar + Formal + Shorten:
- Call 1 — send original text → Grammar Fix → get result 1
- Call 2 — send result 1 → Formal, pass original as original_text → get result 2
- Call 3 — send result 2 → Shorten, pass original as original_text → get result 3
- 3 DB records written, all showing true original vs their respective output
- **Orchestration is on the frontend, backend is stateless**

---

## Conflict Detection System

**Categories:**
- `tone` — Formal, Friendly
- `length` — Shorten, Expand
- `neutral` — Grammar, Bullet, Emoji, Tweetify

**Rules:**
- Two `tone` types conflict — can't select both Formal and Friendly
- Two `length` types conflict — can't select both Shorten and Expand
- `neutral` types never conflict — combine freely with anything

**Lives entirely on frontend** — backend has no conflict awareness

**Known gap** — semantic conflicts like Bullet + Tweetify not detected

---

## Prompt Design

Every transform has its own prompt template:
- Variable 1 — `{text}` — the input text
- Variable 2 — `{additional_instructions}` — user custom instructions
- Every prompt ends with — "Return only the transformed text without any explanations or quotes"
- Temperature 0.3 — consistent, deterministic, not creative
- Max tokens 1000
- Model — llama-3.1-8b-instant
- No system message — everything in user message

**Example — Formal prompt logic:**
"Rewrite in formal professional tone. Return only the text, no explanations."

---

## User Identity System

```javascript
userId = `user_${Date.now()}_${randomString}`
stored in localStorage
```

- Generated once on first use
- Sent with every API request
- Backend uses it to filter history queries
- **No verification** — backend trusts whatever user_id is sent

**Problems:**
- Clear localStorage = lose all history
- New device = new identity = no history
- Anyone knowing your ID can read your history
- Can't do per-user rate limiting properly

**Fix** — Google OAuth, one persistent identity everywhere

---

## Caching System

- In-memory Python dictionary on the server
- Key = `(text, transformation_type, additional_instructions)`
- TTL = 3600 seconds
- Max size = 1000 entries
- Cache hit returns `processing_time: 0.01`
- Two users sending same text share the same cached result

**Critical weakness** — wiped on every server restart, Render restarts frequently, real hit rate is very low in practice

**Fix** — Redis, survives restarts, shared across multiple instances

## What Breaks Under Load

| Concurrent Users | What Happens |
|---|---|
| Up to 15 | Works fine |
| 30+ | SQLite write contention, history writes slow |
| 50+ | Groq rate limits hit, 429 errors on transforms |
| 100+ | Memory pressure from cache, general degradation |

---

## Security Gaps — Be Honest

- **No authentication** — any endpoint callable by anyone
- **CORS has wildcard** — any origin can call the API
- **No rate limiting** — Groq budget fully exposed
- **Prompt injection possible** — additional_instructions unsanitized
- **History unprotected** — know someone's user_id = read their history
- **Cleanup endpoint open** — anyone can wipe all unsaved history

---

## Known Technical Gaps

- No output validation on LLM responses — garbage goes straight to user
- Tweetify doesn't enforce 280 char limit post-generation
- No retry logic — Groq failure = immediate error to user
- SQLite on Render ephemeral filesystem — DB can be wiped on restart
- No loading progress per transform in a chain — one spinner for everything
- Conflict detection only on frontend — backend accepts any combination

---

## Scaling Roadmap — In Priority Order

1. **PostgreSQL** — concurrent writes, persistent storage, production-grade
2. **Rate limiting** — slowapi on FastAPI, protect Groq budget
3. **Redis cache** — survives restarts, shared across instances
4. **Google OAuth** — real user identity, cross-device history
5. **Warm server cron job** — ping every 10 min, eliminate cold starts
6. **Horizontal scaling** — multiple FastAPI instances + load balancer
7. **Request queue** — Celery/Redis Queue between API and Groq
8. **Fallback LLM** — Together AI or Fireworks if Groq goes down
9. **Monitoring** — p95 latency, Groq error rate, DB write failures

## Chrome Extension Specifics

**Manifest V3 key points:**
- Background scripts are Service Workers — ephemeral, not persistent
- Stricter CSP — no remotely hosted scripts, everything bundled
- In-flight API calls die if service worker is killed
- Extension popup is alive only while user has it open

**What happens if popup closes mid-transform:**
- Frontend fetch abandoned, React state gone
- Backend continues processing, Groq call completes
- Result saved to DB even though user never saw it
- User finds it in history when they reopen

## Resume Bullets Explained

**"8 transformation modes and 28 multi-select combinations"**
8 individual transforms, conflict rules reduce valid combinations from theoretical maximum to 28 safe ones.

**"Llama 3.1 via Groq API achieving less than 2s response latency"**
Measured server-side on every request, accurate for single transforms on warm server.

**"Conflict detection"**
Frontend category system — tone vs tone and length vs length blocked, neutral transforms combine freely.

**"7-day history tracking and favorites using SQLite with persistent user storage"**
History filtered by created_at, favorites flagged with is_saved boolean, "persistent" is honest for favorites but limited for history given localStorage identity gap.
